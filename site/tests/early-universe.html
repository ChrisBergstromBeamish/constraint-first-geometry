Blocked, honestly

Test 3 — Early-universe blind predictions

Can the shape predict cosmological observables — the expansion history, the supernova distance ladder, the cosmic microwave background, structure growth — computed first, from the geometry alone, and only then compared to observation? This is the test most exposed to the temptation to peek at the answer first. The honest result is that it is currently blocked, and it is reported that way.

What was done

A forward-model pipeline was built for exactly this purpose: compute cosmological observables — the expansion rate H(z), BAO distances, supernova distance moduli, CMB background consistency, structure growth (S8), and any dark-energy equation-of-state evolution (w0/wa) — from the geometry's own internal inputs only, emit those predictions into a frozen table, and only after that table is written, load observed data for a comparison. This ordering is enforced mechanically: the pipeline has a hard gate that refuses to run the forward integration, and refuses to load any observational data, until an upstream stage reports that the cosmological constant has been computed natively from the geometry (rather than read in from measurement).

That upstream stage has not yet succeeded. It reports Lambda_eff = BLOCKED_PENDING_NATIVE_INPUTS. As a direct, mechanical consequence, the downstream forward-cosmology stage refuses to run:

COSMOLOGY_COMPARISON = BLOCKED_PENDING_NATIVE_LAMBDA
predictions_emitted  = False
comparison_performed = False
observed_inputs_loaded = False

Blind?

Yes, by construction — and this is the entire point of the pipeline's design. The validator that gates this stage actively rejects any attempt to load an observed value (H0, ΩΛ, dark-energy density, S8, BAO posteriors, CMB posteriors) before a native prediction exists, and it rejects any comparison performed before computation. The discipline is explicit in the source documentation: "compare-before-compute is rejected by the validator." So rather than relaxing that rule to produce a number, the honest response was to leave the comparison tables empty and report the block.

Every row is NOT_COMPUTED / NOT_LOADED / NOT_PERFORMED. This is not a failed prediction — it is a prediction that has not been attempted, because its own upstream precondition (a geometry-native value for the cosmological constant) has not been met. A companion validator scan confirmed zero observed cosmological posteriors or numeric fingerprints of observed values appear anywhere in the shipped content for this stage.

Data sources

  • Pipeline documentation and completion report for the forward-cosmology stage of the cosmological-constant closure program, including the typed prediction-table scaffold and the after-the-fact comparison-table scaffold, both built with no values filled in.
  • Comparison targets that would be loaded once the block clears are standard public cosmological posteriors — H0, ΩΛ/ΩM, BAO distance measurements, CMB background parameters, S8 structure-growth measurements — none of which have been loaded yet.
  • The blocking upstream stage (the native computation of the cosmological constant) — reports Lambda_eff = BLOCKED_PENDING_NATIVE_INPUTS.

Why report a blocked test at all

Because the alternative — quietly dropping a test that didn't produce a number, or relaxing the compute-before-compare rule just this once to get a comparison out — is exactly the kind of quiet self-flattery this program is built to refuse. A named, mechanically-enforced block is a stronger statement of honesty than a hidden gap. If and when the cosmological constant is computed natively from the geometry, this same pipeline is already built and gated to run the forward comparison automatically, and to report a miss as a miss if the prediction does not match observation. Until then, the correct and only honest status is BLOCKED_PENDING_NATIVE_LAMBDA.
